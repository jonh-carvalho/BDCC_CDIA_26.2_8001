#### Dados semiestruturados e JSONB

**Objetivos do bloco**

Ao final, a turma deverá conseguir:

>   explicar quando atributos variáveis podem ser armazenados como documento;

Atributos variáveis podem ser armazenados como um documento quando diferentes registros de uma mesma entidade precisam guardar conjuntos de informações distintos, ou quando esses atributos mudam com frequência. Em vez de criar uma coluna para cada possibilidade — muitas delas vazias —, pode-se agrupar esses dados em um campo JSON ou em um documento, por exemplo: `{"cor": "azul", "tamanho": "M"}` para um produto de vestuário e `{"voltagem": "220V", "potencia": "1500W"}` para um eletrodoméstico.

Essa abordagem funciona melhor quando os atributos variáveis são relacionados ao próprio registro e costumam ser lidos ou atualizados em conjunto com ele. É importante, porém, manter como colunas tradicionais os dados estáveis, frequentemente usados em filtros, ordenações ou relacionamentos. Embora bancos de dados possam indexar campos dentro de documentos, consultar e validar esses atributos pode exigir mais cuidado; por isso, o formato documental oferece flexibilidade, mas não deve substituir indiscriminadamente uma estrutura relacional bem definida.

> distinguir `JSON` de `JSONB` no PostgreSQL:

 `JSON` preserva o texto de entrada, enquanto `JSONB` armazena uma representação binária decomposta, mais adequada a consultas e indexação, mas sem preservar espaços, ordem das chaves ou chaves duplicadas;

> escrever consultas básicas com operadores de JSONB;

Por exemplo, localizar entregas com elevador, verificar a presença da chave `boxes` e extrair a temperatura como texto:

```sql
SELECT *
FROM delivery_items
WHERE details @> '{"elevator_required": true}'::jsonb;

SELECT *
FROM delivery_items
WHERE details ? 'boxes';

SELECT
    id,
    details ->> 'temperature_c' AS temperature_c
FROM delivery_items;
```

*   reconhecer a importância de validar os dados e escolher índices adequados.

`JSONB` garante que o conteúdo seja JSON válido, mas não garante que ele siga as regras de cada categoria. Valide campos obrigatórios, tipos e faixas de valores na aplicação ou, quando apropriado, com restrições no banco. Escolha índices conforme as consultas: GIN pode atender buscas de contenção e existência de chaves, enquanto campos consultados frequentemente podem justificar índices de expressão. Como índices ocupam espaço e aumentam o custo de escrita, crie-os com base nos padrões reais de consulta.

**1.1. A dor do relacional em dados variáveis**

Como modelar uma tabela `delivery_items` para uma empresa de logística que transporta de tudo?

*   **Entrega de comida:** temperatura exigida, prazo de validade e condições de conservação.
*   **Entrega de documentos:** peso volumétrico, tipo de envelope e código de rastreio físico.
*   **Entrega de mudança:** quantidade de caixas, necessidade de elevador e equipamentos especiais.

Cada categoria possui atributos próprios, e novas categorias podem surgir. Discuta com a turma onde guardar esses dados sem prejudicar consultas, integridade e manutenção.

**Alternativas de modelagem e seus custos**

*   **Tabela larga:** criar uma coluna para cada atributo possível. Pode gerar muitas colunas sem uso para cada registro, alterações frequentes no esquema e dificuldade para identificar quais campos se aplicam a cada categoria. Valores `NULL` não implicam, por si só, desperdício proporcional de armazenamento.

*   **EAV (`Entity-Attribute-Value`):** guardar cada atributo como uma linha. É flexível, mas consultas que combinam atributos podem exigir múltiplos `JOIN`s ou agregações; tipos, restrições e validações também ficam menos diretos.

*   **Tabelas especializadas:** manter uma tabela principal e tabelas específicas para cada categoria. Favorece estrutura e validação, mas pode tornar consultas e evolução do modelo mais trabalhosas.

**Modelo de documento e abordagem híbrida**

Uma alternativa é manter atributos comuns — como identificador, categoria, destinatário e data — em colunas relacionais e agrupar os atributos específicos em uma coluna `JSONB`.

*   **Schema-on-read** significa interpretar e validar a estrutura quando a aplicação lê ou utiliza o documento; não significa que os dados devam ficar sem regras.
*   A aplicação pode validar cada categoria com um esquema próprio. Restrições também podem ser implementadas no banco quando necessário.
*   Campos usados frequentemente em filtros, ordenações ou relacionamentos podem ser melhores como colunas relacionais ou expressões indexadas.

**1.2. JSON e JSONB no PostgreSQL**

*   `JSON` armazena o texto de entrada e valida se ele é JSON válido. A representação textual é preservada; operações sobre o conteúdo precisam interpretá-lo.
*   `JSONB` armazena uma representação binária decomposta, adequada a consultas e indexação. Não preserva espaços, ordem das chaves nem chaves duplicadas (em geral, prevalece o último valor).
*   `JSONB` costuma ser apropriado para documentos consultados com frequência. `JSON` pode ser útil quando é importante preservar a representação textual original.

**Exemplo:**

```sql
CREATE TABLE delivery_items (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    category   text NOT NULL,
    recipient  text NOT NULL,
    details    jsonb NOT NULL DEFAULT '{}'::jsonb,
    created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO delivery_items (category, recipient, details)
VALUES
    ('food', 'Ana', '{"temperature_c": 4, "expires_on": "2026-06-30"}'),
    ('move', 'Rui', '{"boxes": 12, "elevator_required": true}');
```

Destaque a separação entre atributos comuns e específicos. JSONB não substitui automaticamente chaves estrangeiras, tipos relacionais ou restrições de integridade.

**1.3. Operadores essenciais de JSONB**

Demonstre os operadores usando a coluna `details`. Os exemplos verificam o conteúdo no nível superior, exceto quando a estrutura aninhada é explicitada.

*   **`@>` — contém:** testa se o documento à esquerda contém o JSON à direita.

    ```sql
    SELECT * FROM delivery_items
    WHERE details @> '{"elevator_required": true}'::jsonb;
    ```

*   **`?` — existe chave ou elemento:** verifica uma chave de objeto no nível superior; em arrays, verifica se existe um elemento string correspondente.

    ```sql
    SELECT * FROM delivery_items
    WHERE details ? 'boxes';
    ```

*   **`?|` — existe alguma das chaves:** recebe um array de textos e retorna verdadeiro se ao menos uma chave estiver presente no objeto no nível superior.

    ```sql
    SELECT * FROM delivery_items
    WHERE details ?| ARRAY['boxes', 'temperature_c'];
    ```

*   **`->` e `->>` — navegação:** `->` retorna um valor JSON/JSONB; `->>` retorna seu conteúdo como texto. A navegação pode ser encadeada para acessar campos aninhados.

    ```sql
    SELECT
        details -> 'temperature_c'  AS temperature_json,
        details ->> 'temperature_c' AS temperature_text
    FROM delivery_items;
    ```

    Para comparar o valor como número, faça uma conversão explícita, por exemplo: `(details ->> 'temperature_c')::numeric`.

**Pontos para enfatizar na demonstração**

*   Uma chave ausente e uma chave com valor JSON `null` são situações diferentes. O operador `?` verifica a existência da chave, não se seu valor é não nulo.
*   Operadores de extração podem retornar SQL `NULL` quando o caminho não existe ou não corresponde à estrutura esperada.
*   `->` e `->>` também aceitam índices de array. Exemplo de campo aninhado: `details -> 'address' ->> 'city'`.
*   Em filtros com `@>`, o documento à direita deve refletir a hierarquia desejada.

**1.4. Índices e cuidados de modelagem**

Sem um índice apropriado, uma consulta pode precisar examinar muitas linhas. Para consultas de contenção, demonstre um índice GIN:

```sql
CREATE INDEX delivery_items_details_gin
    ON delivery_items USING GIN (details);
```

O índice GIN padrão (`jsonb_ops`) oferece suporte a uma variedade maior de operadores, incluindo `?` e `?|`. A classe `jsonb_path_ops` pode ser menor e eficiente para determinados usos de contenção (`@>`), mas não atende aos operadores de existência de chave. A escolha depende das consultas reais: índices ocupam espaço e aumentam o custo de escrita.
