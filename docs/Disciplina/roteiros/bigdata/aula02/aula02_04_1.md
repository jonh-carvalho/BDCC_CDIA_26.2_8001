## O Desafio (30 min de trabalho dos alunos)

### Briefing do Desafio (Entregar por escrito)

**Contexto:**
A tabela `delivery_manifests` tem uma coluna `payload JSONB` com estrutura variável. Alguns manifestos têm um array `items` com objetos que contêm as chaves `fragile` (boolean) e `weight_kg` (numérico).

**Requisito:**
Encontrar todos os manifestos que contenham **pelo menos um item** que seja:
- `fragile: true` **E**
- `weight_kg > 5`

**Critérios de Sucesso:**
1. A query deve retornar apenas os manifestos corretos (validar com os dados de exemplo).
2. A query deve ser performática (pensar em índices).
3. O resultado deve incluir: `id`, `manifest_type`, e o `name` do item frágil pesado.

**Dados de Exemplo (já inseridos na tabela):**
```json
{
  "category": "electronics",
  "items": [
    {
      "name": "Monitor 4K OLED",
      "fragile": true,
      "weight_kg": 8.5,
      "insurance_value": 4500
    }
  ],
  "requires_signature": true
}
```
*Este manifesto deve aparecer no resultado (frágil E > 5kg).*

```json
{
  "category": "perishable",
  "items": [
    {
      "name": "Açaí Premium",
      "temp_celsius": -18,
      "weight_kg": 2.5
    }
  ],
  "requires_thermal_bag": true
}
```
*Este NÃO deve aparecer (não é frágil OU peso <= 5kg).*

## Resolução Comentada (15 min)

### Abordagem 1: SQL/JSON Path (Recomendada para PG 12+)

**Código:**
```sql
SELECT 
    id,
    manifest_type,
    payload->'items'->0->>'name' AS item_name
FROM delivery_manifests
WHERE jsonb_path_exists(
    payload, 
    '$.items[*] ? (@.fragile == true && @.weight_kg > 5)'
);
```

**Explicação Didática:**
> *"O PostgreSQL 12+ introduziu o **SQL/JSON Path**, que é uma linguagem de query dentro do JSON, parecida com XPath para XML. A sintaxe `$.items[*]` significa 'todos os elementos do array items'. O `?` é um filtro, e `@` se refere ao elemento atual. O `&&` é o operador AND dentro do path."*

**Vantagens:**
-  Sintaxe elegante e expressiva
-  Execução nativa e otimizada
-  Suporta comparações numéricas dentro do JSON

**Desvantagens:**
-  **Não pode ser indexado com GIN** (o GIN não entende SQL/JSON Path)
-  Para 10 milhões de linhas, vai fazer Seq Scan

---

###  Abordagem 2: Desnormalização com Coluna Gerada (Para Performance Extrema)

**Passo 1: Criar uma coluna gerada (Generated Column)**
```sql
ALTER TABLE delivery_manifests 
ADD COLUMN max_fragile_weight NUMERIC GENERATED ALWAYS AS (
    (SELECT MAX((item->>'weight_kg')::numeric) 
     FROM jsonb_array_elements(payload->'items') AS item 
     WHERE item->>'fragile' = 'true')
) STORED;
```

> *"O que fizemos aqui? Criamos uma coluna que é **calculada automaticamente** toda vez que o `payload` muda. Ela extrai o maior peso entre os itens frágeis. Se não houver itens frágeis, o valor é NULL."*

**Passo 2: Indexar a coluna gerada com B-Tree**
```sql
CREATE INDEX idx_fragile_weight ON delivery_manifests(max_fragile_weight);
```

**Passo 3: Query performática**
```sql
SELECT 
    id,
    manifest_type,
    payload->'items'->0->>'name' AS item_name,
    max_fragile_weight
FROM delivery_manifests
WHERE max_fragile_weight > 5;
```

**Explicação Didática:**
> *"Agora sim! Transformamos um problema de JSON em um problema relacional puro. A coluna `max_fragile_weight` é um número simples, e podemos indexar com B-Tree tradicional. A query é rapidíssima porque usa o índice."*

**Vantagens:**
-  **Extremamente performática** (usa índice B-Tree)
-  Simples de entender e manter
-  Escala para bilhões de linhas

**Desvantagens:**
-  Ocupa espaço em disco adicional (a coluna é materializada)
-  Cálculo síncrono no INSERT/UPDATE (deixa escritas um pouco mais lentas)

###  Comparação de Performance (Demonstrar com EXPLAIN ANALYZE)

**Abordagem 1 (SQL/JSON Path):**
```
Seq Scan on delivery_manifests  (cost=0.00..5000.00 rows=500 width=100) (actual time=0.100..45.000 rows=1 loops=1)
  Filter: jsonb_path_exists(payload, '$.items[*] ? (@.fragile == true && @.weight_kg > 5)'::jsonpath)
  Rows Removed by Filter: 100099
Execution Time: 46.250 ms
```

**Abordagem 2 (Coluna Gerada + Índice):**
```
Index Scan using idx_fragile_weight on delivery_manifests  (cost=0.42..8.44 rows=1 width=100) (actual time=0.050..0.055 rows=1 loops=1)
  Index Cond: (max_fragile_weight > '5'::numeric)
Execution Time: 0.120 ms  <-- 400x mais rápido!
```

> *"Viram a diferença? 46ms vs 0.12ms. Em produção com 10 milhões de linhas, a Abordagem 1 levaria segundos, a Abordagem 2 levaria milissegundos. **Escolha depende do caso de uso**: se a query roda uma vez por dia, use a Abordagem 1 (mais simples). Se roda 1000x por hora, use a Abordagem 2."*

##  Wrap-up e Entregável (5 min)

###  Resumo dos Conceitos da Semana 2

> *"Pessoal, o que aprendemos hoje:*
> 
> 1. **O relacional tem limites** quando os dados são heterogêneos (ex: manifestos de entrega com estruturas diferentes).
> 2. **JSONB** permite schema-on-read: você valida a estrutura na aplicação, não no banco.
> 3. **Índice GIN** é mágico para buscar existência e contenção (`@>`, `?`) em JSON.
> 4. **GIN tem limitações**: não suporta comparações numéricas (`>`, `<`, `BETWEEN`).
> 5. **Soluções avançadas**: SQL/JSON Path (elegante) ou Colunas Geradas (performáticas).
> 
> *O PostgreSQL não é apenas um banco relacional. Ele é um banco **multi-modelo**. Você pode ter o melhor dos dois mundos: transações ACID no relacional + flexibilidade no documento."*

##  Armadilhas Comuns e Como Lidar

### 1. **Aluno tenta usar `@>` com comparação numérica**
```sql
-- ERRADO (vai dar erro de sintaxe)
WHERE payload @> '{"fragile": true, "weight_kg": > 5}'
```
**Como corrigir:**
> *"O operador `@>` espera um JSON válido à direita. `> 5` não é JSON. O GIN não foi feito para comparações de range. Precisamos de outra abordagem."*

### 2. **Aluno usa `jsonb_array_elements` mas não sabe filtrar**
```sql
-- Incompleto
SELECT * FROM delivery_manifests, jsonb_array_elements(payload->'items') AS item
WHERE item->>'fragile' = 'true';
```
**Como corrigir:**
> *"Legal, você explodiu o array. Agora falta filtrar o peso. E mais: você quer o manifesto original, não os itens explodidos. Como você faz isso? Dica: `EXISTS` ou `LATERAL`."*

**Solução com EXISTS:**
```sql
SELECT id, manifest_type
FROM delivery_manifests
WHERE EXISTS (
    SELECT 1 
    FROM jsonb_array_elements(payload->'items') AS item
    WHERE item->>'fragile' = 'true' 
      AND (item->>'weight_kg')::numeric > 5
);
```

### 3. **Aluno não entende a coluna gerada**
> *"Por que `GENERATED ALWAYS AS ... STORED`? O que significa `STORED`?"*

**Explicação:**
> *"`GENERATED ALWAYS` significa que você não pode inserir ou atualizar essa coluna manualmente. Ela é calculada automaticamente. `STORED` significa que o valor é materializado em disco (ocupando espaço). A alternativa seria `VIRTUAL`, que calcula na hora da leitura (mais lento, mas não ocupa disco). Para performance, usamos `STORED`."*

### 4. **Aluno pergunta: "Por que não usar um banco NoSQL como MongoDB?"**
**Resposta:**
> *"Ótima pergunta! MongoDB seria excelente para esse caso de documentos flexíveis. Mas a SwiftTrack já tem PostgreSQL rodando, com transações ACID, backups, replicação. Migrar para MongoDB seria um pesadelo operacional. O PostgreSQL nos dá o melhor dos dois mundos: relacional + documento no mesmo banco. É a filosofia **multi-modelo**."*
