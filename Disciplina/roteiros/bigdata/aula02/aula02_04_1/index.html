    Guia do Instrutor — Bloco 4: O Desafio e Consolidação¶

    Duração: 60 minutos | Objetivo: Consolidar o aprendizado através de um problema real que expõe as limitações do GIN e apresenta soluções avançadas do PostgreSQL.

    Roteiro Narrativo (Storytelling Técnico)¶

    Este é o momento de testar se os alunos realmente entenderam. O desafio propositalmente não pode ser resolvido apenas com o que eles aprenderam até agora (operador @> + GIN). Eles precisam pensar fora da caixa e descobrir recursos avançados do PostgreSQL.

    Abertura do Bloco (5 min)¶

    "Pessoal, vocês acabaram de dominar o índice GIN. Conseguem buscar qualquer chave ou valor dentro de um JSON de forma performática. Mas a vida real não é tão simpática. O time de seguros da SwiftTrack acabou de mandar um Slack urgente:

    'Precisamos de um relatório de todas as entregas que contêm itens frágeis com peso superior a 5kg. É para a apólice de seguro de carga premium.'

    Parece simples, né? Só filtrar 'fragile': true e 'weight_kg' > 5. Mas tem um problema: o GIN é excelente para existência e contenção exata. Ele não sabe o que é 'maior que' (>). Se vocês tentarem fazer @> '{"weight_kg": > 5}', o Postgres vai rir da cara de vocês com um erro de sintaxe.

    Vocês têm 30 minutos. Podem pesquisar na documentação, podem conversar entre si, mas precisam me entregar uma query que resolva isso. E mais: precisa ser performática, porque esse relatório vai rodar todo dia."

    O Desafio (30 min de trabalho dos alunos)¶

    Briefing do Desafio (Entregar por escrito)¶

    Contexto: A tabela delivery_manifests tem uma coluna payload JSONB com estrutura variável. Alguns manifestos têm um array items com objetos que contêm as chaves fragile (boolean) e weight_kg (numérico).

    Requisito: Encontrar todos os manifestos que contenham pelo menos um item que seja: - fragile: true E - weight_kg > 5

    Critérios de Sucesso: 1. A query deve retornar apenas os manifestos corretos (validar com os dados de exemplo). 2. A query deve ser performática (pensar em índices). 3. O resultado deve incluir: id, manifest_type, e o name do item frágil pesado.

    Dados de Exemplo (já inseridos na tabela): 

    {
  "category": "electronics",
  "items": [
    {
      "name": "Monitor 4K OLED",
      "fragile": true,
      "weight_kg": 8.5,
      "insurance_value": 4500
    }
  ],
  "requires_signature": true
}
    Este manifesto deve aparecer no resultado (frágil E > 5kg).

    {
  "category": "perishable",
  "items": [
    {
      "name": "Açaí Premium",
      "temp_celsius": -18,
      "weight_kg": 2.5
    }
  ],
  "requires_thermal_bag": true
}
    Este NÃO deve aparecer (não é frágil OU peso <= 5kg).

    Durante os 30 minutos: Papel do Instrutor¶

    Não dê a resposta! Circule pela sala (ou pelos canais de chat) e faça perguntas orientadoras:

    1. Se o aluno está travado:
    2. "Você já tentou olhar a documentação de JSON Functions and Operators do PostgreSQL?"
    3. "O GIN não resolve comparações numéricas. Que outras funções o Postgres tem para explorar arrays dentro de JSON?"

    4. "Você conhece jsonb_array_elements? O que ela faz?"

    5. Se o aluno está no caminho certo mas lento:

    6. "Legal, você está extraindo o array. Agora como você filtra os elementos desse array?"

    7. "E se você precisasse fazer isso em 10 milhões de linhas, sua query seria rápida? Tem como indexar?"

    8. Se o aluno já resolveu rápido:

    9. "Ótimo! Agora me mostra no EXPLAIN ANALYZE se está usando índice."
    10. "Consegue pensar em uma segunda abordagem diferente?"
    11. "E se eu quisesse criar um índice para essa query específica, como faria?"

    Resolução Comentada (15 min)¶

    Abordagem 1: SQL/JSON Path (Recomendada para PG 12+)¶

    Código: 

    SELECT 
    id,
    manifest_type,
    payload->'items'->0->>'name' AS item_name
FROM delivery_manifests
WHERE jsonb_path_exists(
    payload, 
    '$.items[*] ? (@.fragile == true && @.weight_kg > 5)'
);

    Explicação Didática:

    "O PostgreSQL 12+ introduziu o SQL/JSON Path, que é uma linguagem de query dentro do JSON, parecida com XPath para XML. A sintaxe $.items[*] significa 'todos os elementos do array items'. O ? é um filtro, e @ se refere ao elemento atual. O && é o operador AND dentro do path."

    Vantagens: - Sintaxe elegante e expressiva - Execução nativa e otimizada - Suporta comparações numéricas dentro do JSON

    Desvantagens: - Não pode ser indexado com GIN (o GIN não entende SQL/JSON Path) - Para 10 milhões de linhas, vai fazer Seq Scan

    Abordagem 2: Desnormalização com Coluna Gerada (Para Performance Extrema)¶

    Passo 1: Criar uma coluna gerada (Generated Column) 

    ALTER TABLE delivery_manifests 
ADD COLUMN max_fragile_weight NUMERIC GENERATED ALWAYS AS (
    (SELECT MAX((item->>'weight_kg')::numeric) 
     FROM jsonb_array_elements(payload->'items') AS item 
     WHERE item->>'fragile' = 'true')
) STORED;

    "O que fizemos aqui? Criamos uma coluna que é calculada automaticamente toda vez que o payload muda. Ela extrai o maior peso entre os itens frágeis. Se não houver itens frágeis, o valor é NULL."

    Passo 2: Indexar a coluna gerada com B-Tree 

    CREATE INDEX idx_fragile_weight ON delivery_manifests(max_fragile_weight);

    Passo 3: Query performática 

    SELECT 
    id,
    manifest_type,
    payload->'items'->0->>'name' AS item_name,
    max_fragile_weight
FROM delivery_manifests
WHERE max_fragile_weight > 5;

    Explicação Didática:

    "Agora sim! Transformamos um problema de JSON em um problema relacional puro. A coluna max_fragile_weight é um número simples, e podemos indexar com B-Tree tradicional. A query é rapidíssima porque usa o índice."

    Vantagens: - Extremamente performática (usa índice B-Tree) - Simples de entender e manter - Escala para bilhões de linhas

    Desvantagens: - Ocupa espaço em disco adicional (a coluna é materializada) - Cálculo síncrono no INSERT/UPDATE (deixa escritas um pouco mais lentas)

    Comparação de Performance (Demonstrar com EXPLAIN ANALYZE)¶

    Abordagem 1 (SQL/JSON Path): 

    Seq Scan on delivery_manifests  (cost=0.00..5000.00 rows=500 width=100) (actual time=0.100..45.000 rows=1 loops=1)
  Filter: jsonb_path_exists(payload, '$.items[*] ? (@.fragile == true && @.weight_kg > 5)'::jsonpath)
  Rows Removed by Filter: 100099
Execution Time: 46.250 ms

    Abordagem 2 (Coluna Gerada + Índice): 

    Index Scan using idx_fragile_weight on delivery_manifests  (cost=0.42..8.44 rows=1 width=100) (actual time=0.050..0.055 rows=1 loops=1)
  Index Cond: (max_fragile_weight > '5'::numeric)
Execution Time: 0.120 ms  <-- 400x mais rápido!

    "Viram a diferença? 46ms vs 0.12ms. Em produção com 10 milhões de linhas, a Abordagem 1 levaria segundos, a Abordagem 2 levaria milissegundos. Escolha depende do caso de uso: se a query roda uma vez por dia, use a Abordagem 1 (mais simples). Se roda 1000x por hora, use a Abordagem 2."

    Wrap-up e Entregável (5 min)¶

    Resumo dos Conceitos da Semana 2¶

    "Pessoal, o que aprendemos hoje:

    1. O relacional tem limites quando os dados são heterogêneos (ex: manifestos de entrega com estruturas diferentes).
    2. JSONB permite schema-on-read: você valida a estrutura na aplicação, não no banco.
    3. Índice GIN é mágico para buscar existência e contenção (@>, ?) em JSON.
    4. GIN tem limitações: não suporta comparações numéricas (>, <, BETWEEN).
    5. Soluções avançadas: SQL/JSON Path (elegante) ou Colunas Geradas (performáticas).

    O PostgreSQL não é apenas um banco relacional. Ele é um banco multi-modelo. Você pode ter o melhor dos dois mundos: transações ACID no relacional + flexibilidade no documento."

    Explicação do Entregável¶

    "Para o entregável da Semana 2, vocês precisam me enviar um arquivo week2_deliverable.sql contendo:

    1. Script de criação da tabela delivery_manifests (com a coluna payload JSONB).
    2. Script de criação do índice GIN na coluna payload.
    3. A query do desafio resolvida (pode ser qualquer uma das duas abordagens, mas expliquem qual escolheram e por quê).
    4. Output do EXPLAIN ANALYZE da query do desafio, provando que está performática (ou explicando por que não está).
    5. (Bônus) Se usaram a Abordagem 2, mostrem o script da coluna gerada e o índice B-Tree.

    Critérios de avaliação: - Schema criado corretamente (25%) - Índice GIN implementado (25%) - Query do desafio retorna os dados corretos (30%) - EXPLAIN ANALYZE comentado (20%)

    Prazo de entrega: domingo às 23:59. Dúvidas? Me chamem no Slack."

    Gancho para a Semana 3 (Grafos)¶

    "Hoje vocês aprenderam a modelar dados flexíveis e indexá-los de forma performática. Conseguem achar o motorista que entregou o monitor 4K frágil de 8.5kg. Mas e se eu perguntar:

    'Qual a rota mais curta entre o Hub São Paulo e o Cliente X, passando por no máximo 5 hubs intermediários?'

    O JSONB não sabe responder isso. O relacional também não (JOINs em redes profundas são lentos). Na Semana 3, vamos aprender Apache AGE, uma extensão de grafos para PostgreSQL. Vocês vão modelar a rede logística como nós e arestas, e fazer queries em Cypher (a linguagem do Neo4j). Vai ser épico."

    Armadilhas Comuns e Como Lidar¶

    1. Aluno tenta usar @> com comparação numérica¶

    -- ERRADO (vai dar erro de sintaxe)
WHERE payload @> '{"fragile": true, "weight_kg": > 5}'
    Como corrigir:

    "O operador @> espera um JSON válido à direita. > 5 não é JSON. O GIN não foi feito para comparações de range. Precisamos de outra abordagem."

    2. Aluno usa jsonb_array_elements mas não sabe filtrar¶

    -- Incompleto
SELECT * FROM delivery_manifests, jsonb_array_elements(payload->'items') AS item
WHERE item->>'fragile' = 'true';
    Como corrigir:

    "Legal, você explodiu o array. Agora falta filtrar o peso. E mais: você quer o manifesto original, não os itens explodidos. Como você faz isso? Dica: EXISTS ou LATERAL."

    Solução com EXISTS: 

    SELECT id, manifest_type
FROM delivery_manifests
WHERE EXISTS (
    SELECT 1 
    FROM jsonb_array_elements(payload->'items') AS item
    WHERE item->>'fragile' = 'true' 
      AND (item->>'weight_kg')::numeric > 5
);

    3. Aluno não entende a coluna gerada¶

    "Por que GENERATED ALWAYS AS ... STORED? O que significa STORED?"

    Explicação:

    "GENERATED ALWAYS significa que você não pode inserir ou atualizar essa coluna manualmente. Ela é calculada automaticamente. STORED significa que o valor é materializado em disco (ocupando espaço). A alternativa seria VIRTUAL, que calcula na hora da leitura (mais lento, mas não ocupa disco). Para performance, usamos STORED."

    4. Aluno pergunta: "Por que não usar um banco NoSQL como MongoDB?"¶

    Resposta:

    "Ótima pergunta! MongoDB seria excelente para esse caso de documentos flexíveis. Mas a SwiftTrack já tem PostgreSQL rodando, com transações ACID, backups, replicação. Migrar para MongoDB seria um pesadelo operacional. O PostgreSQL nos dá o melhor dos dois mundos: relacional + documento no mesmo banco. É a filosofia multi-modelo."
