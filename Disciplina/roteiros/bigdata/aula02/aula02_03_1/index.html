    Bloco 3.1: O Problema da Busca Linear¶

    Duração: 20 minutos | Objetivo: Criar a "dor" antes de apresentar a "cura" (índice GIN)

    Roteiro Narrativo (Storytelling Técnico)¶

    Abertura do Bloco¶

    "Pessoal, até agora a gente tem uns 1.000 manifestos na tabela. Parece pouco, mas imagina que a SwiftTrack cresceu: agora são 10 milhões de entregas/mês. O time de operações pediu um relatório urgente: 'quais entregas exigem bolsa térmica?'. Vamos rodar a query e ver o que o Postgres faz por baixo do capô."

    Demonstração Passo a Passo¶

    Passo 1: Preparar o ambiente e garantir escala realista¶

    Este bloco usa PostgreSQL e pressupõe que a tabela deliveries, criada na aula anterior, já exista e contenha ao menos uma entrega. Confira esse pré-requisito:

    SELECT COUNT(*) AS deliveries_disponiveis
FROM deliveries;

    O resultado precisa ser maior que zero. Em seguida, crie a tabela de manifestos caso ela ainda não exista. Se já tiver sido criada no bloco anterior, este comando não altera a tabela:

    CREATE TABLE IF NOT EXISTS delivery_manifests (
    id SERIAL PRIMARY KEY,
    delivery_id INT NOT NULL,
    manifest_type VARCHAR(50) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW(),
    CONSTRAINT fk_delivery
        FOREIGN KEY (delivery_id) REFERENCES deliveries(id)
);

    Para observar a busca sem o índice GIN, remova somente o índice usado nesta demonstração, caso ele tenha sido criado em uma execução anterior:

    DROP INDEX IF EXISTS idx_manifest_payload_gin;

    Antes de inserir a carga, remova apenas os registros sintéticos identificados por este roteiro. Assim, é possível executar o bloco novamente sem duplicar os 100.000 registros:

    DELETE FROM delivery_manifests
WHERE payload @> '{"demo_block_3_1": true}'::jsonb;

    Agora insira 100.000 manifestos fictícios. Os delivery_id são escolhidos ciclicamente entre IDs que realmente existem em deliveries, evitando violação da chave estrangeira:

    WITH available_deliveries AS (
    SELECT
        id,
        ROW_NUMBER() OVER (ORDER BY id) AS row_num
    FROM deliveries
),
delivery_total AS (
    SELECT COUNT(*) AS total
    FROM available_deliveries
)
INSERT INTO delivery_manifests (delivery_id, manifest_type, payload)
SELECT
    d.id,
    CASE (gs.n % 4)
        WHEN 0 THEN 'food'
        WHEN 1 THEN 'fragile'
        WHEN 2 THEN 'documents'
        ELSE 'oversized'
    END,
    CASE (gs.n % 4)
        WHEN 0 THEN '{"category":"perishable","requires_thermal_bag":true,"items":[{"name":"Açaí"}],"demo_block_3_1":true}'::jsonb
        WHEN 1 THEN '{"category":"electronics","fragile":true,"items":[{"name":"TV"}],"demo_block_3_1":true}'::jsonb
        WHEN 2 THEN '{"category":"docs","weight_kg":0.5,"items":[{"name":"Contrato"}],"demo_block_3_1":true}'::jsonb
        ELSE '{"category":"furniture","weight_kg":45,"items":[{"name":"Sofá"}],"demo_block_3_1":true}'::jsonb
    END
FROM generate_series(1, 100000) AS gs(n)
CROSS JOIN delivery_total AS dt
JOIN available_deliveries AS d
    ON d.row_num = ((gs.n - 1) % dt.total) + 1;

    Atualize as estatísticas da tabela para que o otimizador tenha informações recentes antes de montar o plano:

    ANALYZE delivery_manifests;

    Confira a quantidade total e a quantidade gerada por este bloco:

    SELECT
    COUNT(*) AS total_manifestos,
    COUNT(*) FILTER (
        WHERE payload @> '{"demo_block_3_1": true}'::jsonb
    ) AS manifestos_gerados_neste_bloco
FROM delivery_manifests;

    O segundo valor deve ser 100000. O total também inclui quaisquer manifestos que já existiam na tabela.

    Passo 2: A Query "Inocente"¶

    SELECT id, manifest_type, payload->>'category' AS category
FROM delivery_manifests 
WHERE payload @> '{"requires_thermal_bag": true}';

    "Parece inofensiva, né?"

    Passo 3: O Raio-X com EXPLAIN ANALYZE¶

    Agora vem o momento-chave. Rode:

    EXPLAIN ANALYZE
SELECT id, manifest_type, payload->>'category' AS category
FROM delivery_manifests 
WHERE payload @> '{"requires_thermal_bag": true}';

    Exemplo de saída (ilustrativo):¶

    Os custos, tempos e estimativas variam conforme o volume preexistente, a máquina e as estatísticas do banco. A carga deste bloco gera 100.000 linhas, das quais 25.000 têm requires_thermal_bag: true; os registros que já existiam podem alterar os totais observados.

    Seq Scan on delivery_manifests  (cost=0.00..4615.00 rows=25025 width=120) (actual time=0.045..38.210 rows=25000 loops=1)
  Filter: (payload @> '{"requires_thermal_bag": true}'::jsonb)
  Rows Removed by Filter: 75000
Planning Time: 0.125 ms
Execution Time: 39.542 ms

    Passo 4: A Análise Didática (5 min)¶

    Aponte para cada linha do EXPLAIN e explique:

    Linha O que significa Por que é ruim
    Seq Scan O Postgres leu todas as linhas da tabela Como ler um livro inteiro pra achar uma palavra
    Rows Removed by Filter Linhas examinadas que não atenderam ao filtro Trabalho que a busca precisou fazer
    actual time=38.210 ms ~40ms parece rápido, mas... Em produção com 10M linhas, seriam segundos
    rows=25000 Exemplo de quantidade de correspondências O valor real depende dos dados que já existiam

    Perguntas Provocativas:¶

    1. "Se a tabela tivesse 10 milhões de linhas, quanto tempo levaria? (Resposta: ~4 segundos por query simples — inaceitável para API)"
    2. "O Postgres leu o JSON inteiro de cada linha? (Resposta: sim, porque sem índice ele não tem como 'pular' direto pro campo requires_thermal_bag)"
    3. "E se eu quisesse buscar por 5 campos diferentes do JSON ao mesmo tempo? (Resposta: 5x mais lento, cada filtro varre tudo de novo)"

    Ponte para o Próximo Bloco (3.2 — Índice GIN)¶

    "Agora imaginem que vocês são bibliotecários. Toda vez que alguém pede um livro, vocês têm que ir na estante e abrir cada livro, página por página, pra ver se tem a palavra-chave. Exaustivo, né? E se existisse um índice remissivo no final do livro, ou melhor, um catálogo central que diz exatamente em quais livros cada palavra aparece? É isso que o índice GIN faz pro JSONB. Vamos criar ele agora."

    📝 Checklist do Instrutor¶

    • Tabela com 100.000 linhas sintéticas deste bloco, além dos registros que já existiam
    • EXPLAIN ANALYZE (não apenas EXPLAIN) para mostrar tempos reais
    • Destacar visualmente o Seq Scan vs Rows Removed by Filter
    • Fazer a analogia do bibliotecário/catálogo
    • NÃO criar o índice GIN ainda — guarde para o bloco 3.2 como "revelação"

    ⚠️ Armadilhas Comuns¶

    1. Aluno pergunta: "Por que não usar um índice B-Tree normal no payload?"
      Resposta: "B-Tree indexa a coluna inteira como um bloco. Se você buscar @> '{"a":1}', o Postgres teria que comparar o JSON inteiro. GIN desmonta o JSON e indexa cada par chave-valor separadamente."

    2. Aluno pergunta: "E se eu criar um índice só na chave requires_thermal_bag?"
      Resposta: "Ótima pergunta! Isso é um GIN partial index ou expressão indexada. Vamos falar disso em cursos avançados. Por hoje, o GIN na coluna toda já resolve 90% dos casos."

    3. Tempo estourou? Corte a geração de 100k linhas para 10k — o Seq Scan ainda será visível, só menos dramático.
