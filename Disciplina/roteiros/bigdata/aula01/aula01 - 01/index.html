    Schema DDL Completo — SwiftTrack Core¶

    Abaixo está o script SQL completo e comentado para a criação do schema swifttrack_core. Ele foi desenhado para ser didático (com explicações embutidas) e robusto (pronto para produção).

    Pré-requisitos¶

    • Docker instalado (docker --version)
    # Amazon Linux 2023
# Atualizar o sistema e instalar e iniciarDocker
sudo yum update -y
sudo yum install docker -y
sudo service docker start

# Adiciona o usuário padrão ao grupo docker para não precisar de sudo
sudo usermod -a -G docker ec2-user

# Configurar servidor para aceitar conexões SSH com senha:
# Edite o arquivo de configuração do SSH:
sudo nano /etc/ssh/sshd_config

# Descomente ou adicione a linha:
PasswordAuthentication yes

# Reinicie o serviço SSH:
sudo service sshd restart

# Configurar a nova senha do usuário ec2-user:
sudo passwd ec2-user

# Cliente `psql` (opcional) ou DBeaver/pgAdmin
sudo dnf install postgresql16 -y

# Preparo para PostgreSQL com `docker`
# Baixe a imagem:
sudo docker pull pgvector/pgvector:pg16

# Crie um volume para persistência:
sudo docker volume create pgdata

    Reinicie a instância EC2 para aplicar as mudanças de grupo do Docker

    Setup do PostgreSQL 16 (Docker)¶

    Subindo o container:

    docker run -d --name swifttrack-pg -e POSTGRES_PASSWORD=12345678 -e POSTGRES_DB=swifttrack_core -p 5432:5432 -v pgdata:/var/lib/postgresql/data pgvector/pgvector:pg16

    Decisões de Design (Antes do Código)¶

    Escolha Justificativa
    NUMERIC(12,2) para valores financeiros Evita problemas de precisão do FLOAT/REAL. 12,2 permite valores até 99.999.999.999,99 — suficiente para faturamento.
    TIMESTAMPTZ para datas Armazena o fuso horário. Essencial para logística que opera em múltiplas regiões/países.
    VARCHAR para CPF/CNPJ/Placa Preserva zeros à esquerda (001234...) e formatação. Nunca usar INTEGER.
    CHECK em vez de ENUM nativo CHECK é mais portável entre bancos e permite mensagens de erro customizadas.
    Índices em todas as FKs O PostgreSQL não cria índices automaticamente em FKs. Sem eles, DELETE CASCADE e JOINs ficam lentíssimos.

    Script SQL Completo (01_schema.sql)¶

    -- =====================================================================
-- SWIFTTRACK CORE - Schema Relacional
-- Disciplina: Arquiteturas de Dados e Big Data
-- Módulo I - Semana 1: O Núcleo Relacional
-- =====================================================================

-- 1. CRIAÇÃO DO SCHEMA
CREATE SCHEMA IF NOT EXISTS swifttrack_core;
SET search_path TO swifttrack_core;

-- =====================================================================
-- 2. TABELA: CUSTOMERS (Clientes / Contratantes do Frete)
-- =====================================================================
CREATE TABLE IF NOT EXISTS customers (
    id              BIGSERIAL       PRIMARY KEY,
    document        VARCHAR(18)     NOT NULL UNIQUE,  -- CPF (14) ou CNPJ (18)
    name            VARCHAR(200)    NOT NULL,
    email           VARCHAR(255)    NOT NULL UNIQUE,
    address         TEXT,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Comentários sobre a tabela
COMMENT ON TABLE customers IS 'Clientes que contratam o serviço de frete.';
COMMENT ON COLUMN customers.document IS 'CPF ou CNPJ formatado. VARCHAR preserva zeros à esquerda.';

-- =====================================================================
-- 3. TABELA: DRIVERS (Motoristas)
-- =====================================================================
CREATE TABLE IF NOT EXISTS drivers (
    id              BIGSERIAL       PRIMARY KEY,
    name            VARCHAR(200)    NOT NULL,
    cpf             VARCHAR(14)     NOT NULL UNIQUE,
    cnh_number      VARCHAR(11)     NOT NULL UNIQUE,  -- Registro CNH
    cnh_category    CHAR(2)         NOT NULL,         -- C, D ou E
    phone           VARCHAR(20),
    is_active       BOOLEAN         NOT NULL DEFAULT TRUE,
    hired_at        DATE            NOT NULL,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Garante que apenas categorias válidas para caminhão sejam aceitas
ALTER TABLE drivers
    ADD CONSTRAINT chk_drivers_cnh_category
    CHECK (cnh_category IN ('C', 'D', 'E'));

-- =====================================================================
-- 4. TABELA: VEHICLES (Veículos da Frota)
-- =====================================================================
CREATE TABLE IF NOT EXISTS vehicles (
    id              BIGSERIAL       PRIMARY KEY,
    plate           VARCHAR(8)      NOT NULL UNIQUE,
    model           VARCHAR(100)    NOT NULL,
    manufacturer    VARCHAR(100)    NOT NULL,
    year            SMALLINT        NOT NULL,
    capacity_kg     NUMERIC(8,2)    NOT NULL,          -- Capacidade em kg
    status          VARCHAR(20)     NOT NULL DEFAULT 'AVAILABLE',
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Valida placa no padrão brasileiro (antigo ABC-1234 ou Mercosul ABC1D23)
ALTER TABLE vehicles
    ADD CONSTRAINT chk_vehicles_plate_format
    CHECK (plate ~ '^[A-Z]{3}-?[0-9][A-Z0-9][0-9]{2}$');

ALTER TABLE vehicles
    ADD CONSTRAINT chk_vehicles_status
    CHECK (status IN ('AVAILABLE', 'IN_USE', 'MAINTENANCE', 'DECOMMISSIONED'));

ALTER TABLE vehicles
    ADD CONSTRAINT chk_vehicles_year
    CHECK (year BETWEEN 1980 AND 2100);

-- =====================================================================
-- 5. TABELA: DELIVERIES (Entregas — o evento logístico)
-- =====================================================================
CREATE TABLE IF NOT EXISTS deliveries (
    id              BIGSERIAL       PRIMARY KEY,
    -- Relacionamentos com clientes, motoristas e veículos one-to-many
    customer_id     BIGINT          NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
    driver_id       BIGINT          REFERENCES drivers(id) ON DELETE SET NULL,
    vehicle_id      BIGINT          REFERENCES vehicles(id) ON DELETE SET NULL,

    origin_address  TEXT            NOT NULL,
    destination_address TEXT        NOT NULL,
    weight_kg       NUMERIC(8,2)    NOT NULL,

    status          VARCHAR(20)     NOT NULL DEFAULT 'PENDING',

    scheduled_at    TIMESTAMPTZ,                        -- Quando foi agendada
    picked_up_at    TIMESTAMPTZ,                        -- Quando foi coletada
    delivered_at    TIMESTAMPTZ,                        -- Quando foi entregue

    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- DESAFIO DE CONSTRAINT: Status da entrega
-- Permite apenas os status válidos: PENDING, IN_TRANSIT, DELIVERED, CANCELED
ALTER TABLE deliveries
    ADD CONSTRAINT chk_deliveries_status
    CHECK (status IN ('PENDING', 'IN_TRANSIT', 'DELIVERED', 'CANCELED'));

-- Regra de negócio: só pode ter data de entrega se status for DELIVERED
ALTER TABLE deliveries
    ADD CONSTRAINT chk_deliveries_delivered_at
    CHECK (
        (status = 'DELIVERED' AND delivered_at IS NOT NULL)
        OR
        (status <> 'DELIVERED' AND delivered_at IS NULL)
    );

-- Regra de negócio: peso deve ser positivo
ALTER TABLE deliveries
    ADD CONSTRAINT chk_deliveries_weight
    CHECK (weight_kg > 0);

-- =====================================================================
-- 6. TABELA: INVOICES (Faturas — o evento financeiro)
-- =====================================================================
CREATE TABLE IF NOT EXISTS invoices (
    id              BIGSERIAL       PRIMARY KEY,
    -- Relacionamentos one-to-one com delivery e customer
    delivery_id     BIGINT          NOT NULL REFERENCES deliveries(id) ON DELETE RESTRICT,
    customer_id     BIGINT          NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,

    invoice_number  VARCHAR(20)     NOT NULL UNIQUE,    -- Número da NF
    series          CHAR(3)         NOT NULL DEFAULT '001',

    total_value     NUMERIC(12,2)   NOT NULL,           -- Valor total da fatura
    tax_value       NUMERIC(12,2)   NOT NULL DEFAULT 0, -- Impostos
    net_value       NUMERIC(12,2)   NOT NULL,           -- Valor líquido

    status          VARCHAR(20)     NOT NULL DEFAULT 'ISSUED',

    issued_at       TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    due_date        DATE            NOT NULL,
    paid_at         TIMESTAMPTZ,

    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- DESAFIO DE CONSTRAINT: Valor da fatura DEVE ser positivo
ALTER TABLE invoices
    ADD CONSTRAINT chk_invoices_total_value
    CHECK (total_value > 0);

-- DESAFIO DE CONSTRAINT: Valor líquido DEVE ser positivo
ALTER TABLE invoices
    ADD CONSTRAINT chk_invoices_net_value
    CHECK (net_value >= 0);

-- Regra de negócio: valor líquido = total - impostos
ALTER TABLE invoices
    ADD CONSTRAINT chk_invoices_values_consistency
    CHECK (net_value = total_value - tax_value);

-- 
ALTER TABLE invoices
    ADD CONSTRAINT chk_invoices_status
    CHECK (status IN ('ISSUED', 'PAID', 'CANCELED', 'OVERDUE'));

-- Só pode ter data de pagamento se status for PAID
ALTER TABLE invoices
    ADD CONSTRAINT chk_invoices_paid_at
    CHECK (
        (status = 'PAID' AND paid_at IS NOT NULL)
        OR
        (status <> 'PAID' AND paid_at IS NULL)
    );

-- =====================================================================
-- 7. ÍNDICES B-TREE (Performance)
-- =====================================================================
-- Regra de ouro: TODO Foreign Key deve ter índice!

-- Customers
CREATE INDEX idx_customers_document ON customers(document);

-- Drivers
CREATE INDEX idx_drivers_cpf        ON drivers(cpf);
CREATE INDEX idx_drivers_is_active  ON drivers(is_active) WHERE is_active = TRUE; -- Índice parcial!

-- Vehicles
CREATE INDEX idx_vehicles_plate     ON vehicles(plate);
CREATE INDEX idx_vehicles_status    ON vehicles(status);

-- Deliveries (FKs + colunas de filtro frequente)
CREATE INDEX idx_deliveries_customer_id   ON deliveries(customer_id);
CREATE INDEX idx_deliveries_driver_id     ON deliveries(driver_id);
CREATE INDEX idx_deliveries_vehicle_id    ON deliveries(vehicle_id);
CREATE INDEX idx_deliveries_status        ON deliveries(status);              -- Filtro frequente
CREATE INDEX idx_deliveries_scheduled_at  ON deliveries(scheduled_at);        -- Ordenação por data

-- Invoices (FKs + colunas de filtro frequente)
CREATE INDEX idx_invoices_delivery_id     ON invoices(delivery_id);
CREATE INDEX idx_invoices_customer_id     ON invoices(customer_id);           -- Filtro frequente
CREATE INDEX idx_invoices_status          ON invoices(status);
CREATE INDEX idx_invoices_due_date        ON invoices(due_date);              -- Busca por vencimento
CREATE INDEX idx_invoices_issued_at       ON invoices(issued_at);

-- =====================================================================
-- 8. TRIGGER DE UPDATED_AT (Boas práticas)
-- =====================================================================
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_customers_updated_at
    BEFORE UPDATE ON customers
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

CREATE TRIGGER trg_deliveries_updated_at
    BEFORE UPDATE ON deliveries
    FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

    Queries de Validação (Para o Aluno Testar as Constraints)¶

    Depois de rodar o script acima, o aluno pode testar se as constraints estão funcionando. Todas as queries abaixo DEVEM falhar com erro de constraint:

    -- Deve falhar: valor negativo na fatura
INSERT INTO swifttrack_core.invoices 
    (delivery_id, customer_id, invoice_number, total_value, net_value, due_date)
VALUES (1, 1, 'NF001', -100.00, -100.00, '2026-10-10');
-- ERRO: new row for relation "invoices" violates check constraint "chk_invoices_total_value"

-- Deve falhar: status inválido em entrega
INSERT INTO swifttrack_core.deliveries 
    (customer_id, origin_address, destination_address, weight_kg, status)
VALUES (1, 'SP', 'RJ', 100, 'FINISHED');
-- ERRO: new row for relation "deliveries" violates check constraint "chk_deliveries_status"

-- Deve falhar: placa de veículo com formato inválido
INSERT INTO swifttrack_core.vehicles 
    (plate, model, manufacturer, year, capacity_kg)
VALUES ('123-ABCD', 'Truck', 'Volvo', 2020, 10000);
-- ERRO: new row for relation "vehicles" violates check constraint "chk_vehicles_plate_format"

-- Deve falhar: categoria de CNH inválida
INSERT INTO swifttrack_core.drivers 
    (name, cpf, cnh_number, cnh_category, hired_at)
VALUES ('João', '123.456.789-00', '12345678900', 'A', '2024-01-01');
-- ERRO: new row for relation "drivers" violates check constraint "chk_drivers_cnh_category"

-- Deve falhar: delivered_at preenchido mas status não é DELIVERED
INSERT INTO swifttrack_core.deliveries 
    (customer_id, origin_address, destination_address, weight_kg, status, delivered_at)
VALUES (1, 'SP', 'RJ', 100, 'IN_TRANSIT', NOW());
-- ERRO: violates check constraint "chk_deliveries_delivered_at"

    Verificando os Índices Criados¶

    Para confirmar que os índices B-Tree foram criados, o aluno pode rodar:

    -- Lista todos os índices do schema swifttrack_core
SELECT 
    tablename,
    indexname,
    indexdef
FROM pg_indexes
WHERE schemaname = 'swifttrack_core'
ORDER BY tablename, indexname;

    Ou para ver o plano de execução de uma query (mostrando se o índice está sendo usado):

    EXPLAIN ANALYZE 
SELECT * FROM swifttrack_core.deliveries 
WHERE status = 'IN_TRANSIT';
-- O plano pode usar o índice ou uma varredura sequencial, conforme o volume e a distribuição dos dados.

    Pontos de Discussão para a Aula¶

    1. Por que BIGSERIAL e não SERIAL? Para tabelas de alto volume (entregas, faturas), BIGSERIAL (8 bytes, até 9 quintilhões) evita problemas futuros de estouro de ID.

    2. ON DELETE RESTRICT vs CASCADE: Em tabelas financeiras (invoices), nunca usar CASCADE. Se um cliente for deletado, queremos que o banco bloqueie a operação, não que apague faturas silenciosamente.

    3. Índice Parcial (WHERE is_active = TRUE): Um índice menor, mais rápido e que ocupa menos disco. Só indexa motoristas ativos — que são o que realmente importa nas queries do dia a dia.

    4. NUMERIC vs DECIMAL: No PostgreSQL, são sinônimos. Ambos garantem precisão exata — essenciais para dinheiro.

    Aplicando o 01_schema.sql no Docker (sem docker-compose)¶

    Existem 3 formas principais de fazer isso. Vou apresentar da mais simples para a mais robusta.

    Opção 1: Pipe direto (MAIS RÁPIDA — Recomendada)¶

    Essa é a forma mais elegante: você "alimenta" o psql dentro do container com o conteúdo do seu arquivo local, sem precisar copiar nada.

    # Execute este comando no terminal, na pasta onde está o arquivo 01_schema.sql
cat 01_schema.sql | docker exec -i swifttrack-pg psql -U postgres -d swifttrack_core

    Explicando o comando:¶

    Parte Função
    cat 01_schema.sql Lê o conteúdo do arquivo SQL
    \| (pipe) Envia esse conteúdo para o próximo comando
    docker exec -i swifttrack-pg Executa um comando dentro do container (a flag -i mantém o stdin aberto)
    psql -U postgres -d swifttrack_core Conecta ao banco swifttrack_core com o usuário postgres

    Saída esperada (sucesso):¶

    CREATE SCHEMA
CREATE TABLE
COMMENT
CREATE TABLE
...
CREATE INDEX
CREATE FUNCTION
CREATE TRIGGER

    Opção 2: Copiar o arquivo para o container (MAIS ROBUSTA)¶

    Se o arquivo for grande ou você quiser inspecioná-lo dentro do container depois:

    # 1. Copia o arquivo para dentro do container
docker cp 01_schema.sql swifttrack-pg:/tmp/01_schema.sql

# 2. Executa o SQL dentro do container
docker exec swifttrack-pg psql -U postgres -d swifttrack_core -f /tmp/01_schema.sql

# 3. (Opcional) Remove o arquivo temporário
docker exec swifttrack-pg rm /tmp/01_schema.sql

    Vantagem: Se der erro no meio, você pode entrar no container e editar o arquivo sem precisar reenviar.

    Opção 3: Usar psql local (se tiver instalado na sua máquina)¶

    Como a porta 5432 foi exposta no docker run, você pode conectar diretamente da sua máquina:

    # No Linux/Mac:
psql -h localhost -p 5432 -U postgres -d swifttrack_core -f 01_schema.sql

# A senha é: secret

    Ou, se quiser evitar digitar a senha toda hora: 

    PGPASSWORD=secret psql -h localhost -p 5432 -U postgres -d swifttrack_core -f 01_schema.sql

    ** Limitação:** Requer ter o psql instalado na máquina host.

    Validando que Funcionou¶

    Depois de executar qualquer uma das opções acima, confirme que o schema foi criado:

    # Entra no container interativamente
docker exec -it swifttrack-pg psql -U postgres -d swifttrack_core

    Dentro do psql, rode:

    -- Lista as tabelas criadas
\dt swifttrack_core.*

-- Lista os índices
\di swifttrack_core.*

-- Conta as tabelas (deve retornar 5)
SELECT COUNT(*) FROM information_schema.tables 
WHERE table_schema = 'swifttrack_core' AND table_type = 'BASE TABLE';

-- Sai do psql
\q

    Problemas Comuns e Soluções¶

    Erro: docker: "exec" requires at least 2 arguments¶

    Causa: Esqueceu o -i no pipe. Solução: Use docker exec -i (não apenas docker exec).

    Erro: psql: FATAL: database "swifttrack_core" does not exist¶

    Causa: O container foi criado sem a variável POSTGRES_DB. Solução: Reconstrua o container: 

    docker rm -f swifttrack-pg
docker run --name swifttrack-pg \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=swifttrack_core \
  -p 5432:5432 -d postgres:16

    Erro: could not find file "/tmp/01_schema.sql"¶

    Causa: Esqueceu o docker cp antes. Solução: Use a Opção 1 (pipe) que não precisa copiar.

    Erro: permission denied no arquivo¶

    Causa: Permissões do Linux. Solução: chmod +r 01_schema.sql

    Dica Bônus: Script de "Reset Total"¶

    Se você quiser recriar o schema do zero (útil durante os testes da aula), crie um arquivo reset.sh:

    #!/bin/bash
# Reseta o banco e reaplica o schema

docker exec swifttrack-pg psql -U postgres -c "DROP SCHEMA IF EXISTS swifttrack_core CASCADE;"
cat 01_schema.sql | docker exec -i swifttrack-pg psql -U postgres -d swifttrack_core
echo "Schema recriado com sucesso!"

    Depois é só rodar: 

    chmod +x reset.sh
./reset.sh

    Resumo Prático¶

    Para a aula, a Opção 1 é a mais didática e rápida:

    cat 01_schema.sql | docker exec -i swifttrack-pg psql -U postgres -d swifttrack_core
